# WebP 轉檔與資源量測

轉檔操作以 [菜譜插畫流程](../.claude/skills/recipe-making/illustration.md#轉檔) 為準。預覽圖與縮圖總表仍用專案既有的 Sharp；WebP 編碼改用系統 cwebp，成品由同套件的 dwebp 完整解碼驗證。這是本地內容製作與測試的依賴，網站建置不需要重新編碼原始 PNG。CI 在共用 verify action 安裝 WebP 工具。

## 量測方法

2026-10-10，macOS arm64、Node.js 24.21.0、Sharp 0.35.2、cwebp 1.6.0。用 `/usr/bin/time -l` 記錄實際耗時、user 加 sys 的 CPU 總時間、maximum resident set size；循序執行，各組三輪。數字包含程序啟動成本；耗時與 CPU 取整批總和的中位數，記憶體取各次程序尖峰的最大值，不是整台機器或並行工作的總記憶體。

原圖為本地生成的東坡肉成品、蟹黃豆腐材料、炸蚵仔步驟各一張，均為 1536×1024、RGB PNG。它們品質 80 就符合大小限制。對照路徑：原有 img.mjs、預先產生一次 raw pixels 後重用的 Sharp、直接 cwebp。cwebp 使用 `-q 80 -m 4 -mt`，與原有 Sharp 輸出逐位元相同。

| 路徑             | 三張總耗時中位數 | CPU 總時間中位數 | 最大程序尖峰 RSS |
| ---------------- | ---------------: | ---------------: | ---------------: |
| 原有 Sharp       |          0.42 秒 |          0.43 秒 |         89.0 MiB |
| 一次縮放的 Sharp |          0.39 秒 |          0.40 秒 |         90.1 MiB |
| 直接 cwebp       |          0.24 秒 |          0.24 秒 |         15.1 MiB |

單張成品大小依序為 174524、180598、141226 bytes。這批直接 cwebp 約降低 43% 實際耗時、44% CPU 總時間、83% 程序尖峰記憶體。這是直接 CLI 的量測，不能將該比例當成正式 Node 批次入口的保證；入口仍有 Node、Sharp metadata 與成品驗證成本。

## 邊界補測

用同一張成品原圖另製作 2048×1024 寬圖與 1024×1536 直圖，測試 cwebp 自行置中裁切與縮放。輸出均為 1536×1024，分別 179116 與 146524 bytes，直圖縮圖左右比對構圖一致。不同縮放器的結果不保證逐位元相同，因此正式流程保留 Sharp 的原有 `fit: "cover"`，只預處理一次，再交給 cwebp 編碼。

另以固定種子的雜訊混合原圖製作壓力測試輸入；這不是正式菜譜原圖。30% 雜訊案例從品質 80 的 616966 bytes 降到品質 30 的 266908 bytes，需 11 次編碼。兩種編碼器在各品質的檔案大小相同。三輪單張結果如下；cwebp 此表包含 Node 包裝程序，與上表直接 CLI 不同。

| 路徑             | 耗時中位數 | CPU 總時間中位數 | 最大程序尖峰 RSS |
| ---------------- | ---------: | ---------------: | ---------------: |
| 原有 Sharp       |    1.37 秒 |          1.38 秒 |        103.5 MiB |
| 一次縮放的 Sharp |    1.22 秒 |          1.23 秒 |        104.6 MiB |
| Node 包裝 cwebp  |    1.32 秒 |          1.34 秒 |         73.3 MiB |

35% 雜訊案例在品質 30 仍為 313228 bytes，兩條路徑都不達標。正式流程應回報失敗並保留既有成品，不能以降低品質下限通過。

## 正式入口的整合量測

正式入口增加暫存檔、成品驗證與批次處理後，重新量測同一組三張原圖。初版以 Sharp raw buffer 驗證，批次尖峰 RSS 升至 141.4 MiB；關閉 Sharp 快取並改用 stats 仍約 107 MiB。因此最終改由 dwebp 完整解碼為 PPM，輸出送到系統空裝置，避免完整像素緩衝區累積在長時間執行的 Node 程序。Sharp 僅用於 metadata 與非標準尺寸預處理，轉檔時關閉其快取。dwebp 與 cwebp 都由同一個系統 WebP 套件提供，參考 [dwebp 官方文件](https://developers.google.com/speed/webp/docs/dwebp)。

原有單張流程逐張執行三張的基準為 0.42 秒實際耗時、0.43 秒 CPU 總時間、89.0 MiB 最大程序 RSS。原生解碼驗證的批次原型三輪量測為 0.35 秒耗時中位數、0.37 秒 CPU 中位數、83.1 MiB 最大程序 RSS；約省 17% 耗時、14% CPU 與 7% 記憶體，操作由三個命令減為一個。這比直接 CLI 的節省小得多，應以正式入口的數字判斷整體改善。

完整建置結束後，用修改前的 Git 版本與正式批次入口交錯重跑五輪，避免兩組固定執行順序；同一組原圖，兩組的三張成品逐位元相同。結果如下，作為最終比較：

| 路徑                   | 三張總耗時中位數 | CPU 總時間中位數 | 最大程序尖峰 RSS |
| ---------------------- | ---------------: | ---------------: | ---------------: |
| 修改前，三次單張命令   |          0.50 秒 |          0.52 秒 |         90.5 MiB |
| 正式入口，一次批次命令 |          0.42 秒 |          0.44 秒 |         83.3 MiB |

本次正式比較約省 16% 耗時、15% CPU 與 8% 程序尖峰記憶體。絕對數字會隨機器負載變動；原始紀錄與比較腳本位於 `.scratch/webp-benchmark/comparison-final.json` 與 `compare-final.py`。

## 判斷與限制

採用 cwebp 的主要證據是標準尺寸原圖的資源消耗降低，以及保持同一品質階梯的編碼結果；多輪重試案例沒有明顯速度優勢。循序批次用於控制同時工作的數量與操作次數，不表示單張 CPU 峰值一定更低。`-mt` 可使用多執行緒，但 CPU 總時間才是本次資源指標。

保留品質 80→30、每次降 5，不改成 `-size`：後者也會多輪編碼，且只是嘗試接近目標大小，仍需驗證。參考 [cwebp 官方文件](https://developers.google.com/speed/webp/docs/cwebp)。

本次樣本小，沒有涵蓋所有生成圖片、其他作業系統、編碼器版本或機器負載。原始量測、實驗腳本與輸出保留於本地 `.scratch/webp-benchmark/`；正式程式的行為測試涵蓋成功、預處理、降品質、超限、批次與原檔保留，不設定機器相關的效能門檻。

若未來需撤回，將 WebP 編碼恢復為 Sharp，移除只供轉檔測試使用的系統 WebP 依賴即可；成品格式與網站內容不需要遷移。

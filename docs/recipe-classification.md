# 菜譜分類與配餐指南

分類先看端上桌的料理主角，再決定它在套餐中擔任什麼角色。瀏覽分類與配餐角色分開保存，不能因為有空心菜就把沙茶羊肉當作套餐的蔬菜料理。

## 三層判斷

1. `category` 決定上桌形式：非湯料理、主食、湯。主食不參與四菜一湯／五菜一湯；湯只進湯位。本次遷移不改任何既有菜譜的 `category` 或 `mealCandidate`，湯與鍋物的歷史邊界另行討論。
2. `dishKinds` 決定瀏覽主角：`vegetable`（蔬菜，含菇類）、`meat`（肉類）、`seafood`（海鮮）、`egg-bean`（蛋豆）。非湯料理至少一個，不重複；真正並列的主角可以有多個。主食與湯填 `[]`，瀏覽直接使用其 `category`。
3. `vegetable`、`protein` 只決定配餐角色，不再產生首頁分類。每套仍由不同的兩道菜滿足兩種角色：一道蔬菜為主的菜，以及另一道肉、海鮮或蛋豆為主的菜。蔬菜角色只限 `dishKinds: [vegetable]` 且 `protein: false`；包含蔬菜的雙主角菜不抵充這個位置。

`mealCandidate` 仍是站主明確決定的參與資格。不是每篇公開菜譜都要參與套餐；分類調整不等於自動開啟或關閉候選資格。草稿一律排除，無論其候選旗標如何。

## 如何辨認主角

- 同看材料、實際用量、處理方式、成品形態和上桌用途，不只看標題或舊旗標。
- 肉末澆料、起鍋撒的蔥花、醃料蛋液與鹹蛋裹醬，可以只是配料或調味，不因出現在材料表就增加主角。
- 一道料理有兩種完整且並列的主料時，可以是雙主角；「有兩種材料」本身不夠。
- 不以克數、比例或推定營養值硬判。材料只有一把、一盒而未註重量時，不自行換算。食材名稱與未知重量照原配方保留。
- `vegetable` 不是素食宣稱，`protein` 不是蛋白質含量認證。這兩個欄位只描述本站套餐安排，不提供營養或醫療判斷。

每篇必填 `classificationReason`，用一句具體理由交代主角與配料用途；草稿也要填。理由只供編輯與內容檢查，不顯示在公開頁面、搜尋索引或分享文案。判據不足時在送審中註明邊界，不用程式依名稱或關鍵字補分類。

## 已確認的例子

| 菜譜     | 瀏覽主角   | 配餐角色       | 判斷                                                 |
| -------- | ---------- | -------------- | ---------------------------------------------------- |
| 沙茶羊肉 | 肉類       | 肉、海鮮或蛋豆 | 羊肉是主角，空心菜與洋蔥搭配；不抵充蔬菜位           |
| 肉燥菠菜 | 蔬菜       | 蔬菜           | 菠菜是成品主角，肉燥是澆料                           |
| 麻婆豆腐 | 蛋豆       | 肉、海鮮或蛋豆 | 豆腐是主角，肉末組成醬料                             |
| 番茄炒蛋 | 蔬菜、蛋豆 | 肉、海鮮或蛋豆 | 番茄與蛋分炒再合，兩者並列；套餐仍另留蔬菜為主的一道 |

筍香炒肉絲等混合料理要照本版材料與做法逐篇判斷，不沿用前次「有菜就補蔬菜旗標」的建議。全量遷移的個別判據見 [逐篇審核表](recipe-classification-review.md)。

## 作者與審查檢核

- 填好 `category`、`dishKinds`、`classificationReason`、候選資格與兩個配餐角色，逐項給理由。
- 非湯料理至少一種配餐角色；`protein: true` 須有肉、海鮮或蛋豆主角。蔬菜單主角不能同時填 `protein: true`。
- 主食與湯沒有非湯料理的主角標記與配餐角色；主食不得為候選。schema 對草稿一樣檢查。
- 主角資料不可從組餐布林反推，角色也不可用 `dishKinds.includes("vegetable")` 自動補真。
- 跑格式、schema、正式內容檢查、真實菜譜回歸、首頁與搜尋篩選、四菜／五菜抽選測試。部署前除菜／湯數量門檻外，也確認角色足以形成套餐；不能降低門檻讓部署通過。

只有分類與角色變動時，應確認配方文字、材料用量、步驟、圖片、來源、草稿狀態和候選資格未被順帶更改。新增或改寫配方仍須遵守既有來源核准與照抄檢查；分類審閱不代表核准新配方或解封草稿。

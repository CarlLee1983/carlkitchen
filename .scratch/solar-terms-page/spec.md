# 節氣總覽頁規格

Type: spec
Status: open
Label: ready-for-agent

本規格整理自 2026-10-08 的 grill-with-docs 討論。詞彙見 `GLOSSARY.md`〈時令〉；架構決定見 ADR 0006、0007、0008。

## Problem Statement

首頁「這個時節」只告訴讀者現在是哪個節氣、何時交節，沒有下文：讀者看到「寒露」，不知道這時節該買什麼、煮什麼，也看不到其他節氣。站內已有 24 張節氣插畫，卻只以 64px 縮圖出現；食材條目雖寫了臺灣產期，讀者卻無法從「時節」這條線找到它們。

## Solution

新增一張節氣總覽頁：依春夏秋冬分四組、從立春排起，每個節氣以現有插畫為主圖，附一兩句天文與氣候背景，並列出站主挑選的當令食材條目連結。頁面依讀者當下時間標出目前節氣，並填上各節氣今年的交節日期與資料出處。首頁「這個時節」的節氣列連到總覽頁上該節氣的位置。內容整頁一次送審，經站主核准來源與審閱後發布。

## User Stories

1. 身為讀者，我想從首頁的節氣列點進去，直接看到該節氣的介紹，以便知道這個時節有什麼可以煮。
2. 身為讀者，我想在一頁內看到全部二十四節氣，以便瀏覽一整年的時令變化。
3. 身為讀者，我想看到節氣依春夏秋冬分組、從立春排起，以便用熟悉的方式找到節氣。
4. 身為讀者，我想每個節氣都有插畫，以便快速辨認並感受季節氛圍。
5. 身為讀者，我想讀到每個節氣一兩句天文與氣候背景，以便理解這個節氣的意思。
6. 身為讀者，我想看到每個節氣的當令食材，並能點進食材條目，以便決定這時節買什麼。
7. 身為讀者，我想在沒有當令食材的節氣看到乾淨的介紹而不是空清單，以便不被誤導。
8. 身為讀者，我想看到「產期依地區與年度變動，僅供參考」的提醒，以便不把節氣與食材的對應當成定論。
9. 身為讀者，我想看到各節氣今年的交節日期與時刻，以便安排時令料理。
10. 身為讀者，我想知道交節時刻的出處是中央氣象署或天文推算，以便判斷資料可信度。
11. 身為讀者，我想一眼看出目前所在的節氣，以便不必自己對照日期。
12. 身為讀者，我想在交節時刻一過，重新開啟頁面就看到新的目前節氣，以便頁面不停在網站建置當下。
13. 身為未執行 JavaScript 的讀者，我想仍看到全部節氣的插畫、說明與食材，以便頁面主體不依賴腳本。
14. 身為讀者，我想在站內搜尋「冬至」等節氣名時找到總覽頁，以便從搜尋進入。
15. 身為手機讀者，我想在窄螢幕上順暢瀏覽四季分組與插畫，以便不需要橫向捲動。
16. 身為使用螢幕閱讀器的讀者，我想每張插畫都有「<節氣>節氣插畫」替代文字、四季分組有標題結構，以便理解頁面。
17. 身為站主，我想所有節氣說明共用一個我核准的權威來源，以便一次核准、出處一致。
18. 身為站主，我想來源紀錄沿用專題來源紀錄的格式、放在公開輸出之外，以便維護方式與專題一致且來源網址不外洩。
19. 身為站主，我想由我為每個節氣挑選當令食材，依據是該食材條目的產期文字，以便不必另找產期來源。
20. 身為站主，我想之後新增食材條目時，只改節氣資料就能補上當令食材，以便內容逐步累積。
21. 身為站主，我想內容檢查在缺任何一個節氣時報錯，以便頁面不會少一格。
22. 身為站主，我想內容檢查在節氣說明的來源未登錄於來源紀錄時報錯，以便每段說明都有核准來源。
23. 身為站主，我想內容檢查在當令食材指向不存在或未發布的食材條目時報錯，以便頁面不出現壞連結。
24. 身為站主，我想頁面文案同樣受「不得提 AI 或試做」檢查，以便符合 ADR 0004。
25. 身為站主，我想核准來源網址不出現在建置輸出，以便符合既有的洩漏檢查。
26. 身為站主，我想透過 PR 審閱整頁內容，合入即發布，以便不必管理逐筆草稿。
27. 身為開發者，我想用環境變數切換節氣內容目錄與來源紀錄目錄，以便測試與 e2e 使用固定資料。
28. 身為開發者，我想節氣識別值與現有插畫檔名相同，以便首頁、總覽頁與插畫以同一組鍵對應。

## Implementation Decisions

- **新內容集合「節氣」**：每個節氣一筆結構化資料，固定 24 個識別值，與現有節氣插畫檔名相同（`lichun`、`lidong` 等）。不寫成專題（ADR 0008）。
- **資料欄位**：節氣名稱、所屬季節（由識別值決定亦可，實作者擇一並保持單一真相）、說明（一兩句）、當令食材（已發布食材條目識別值陣列，可為空）。不設 `draft`。
- **來源紀錄**：另一個目錄，格式沿用專題來源紀錄的 `sources`（`title`、`url`）與對照；對照以節氣識別值取代專題的段落標題。不進內容集合、不進公開輸出，只由內容檢查讀取。
- **環境變數**：比照 `TOPICS_DIR`／`TOPIC_SOURCES_DIR`，新增節氣內容目錄與節氣來源紀錄目錄兩個變數；e2e 與單元測試指向 fixtures。
- **總覽頁**：網址 `/solar-terms/`；每個節氣一個以識別值為 `id` 的區塊，供首頁以錨點連結。四季各一個標題，依立春起排序。插畫沿用 `src/assets/solar-terms/`，替代文字沿用「<節氣>節氣插畫」。頁面附「產期依地區與年度變動，僅供參考」提醒。
- **今年日期與目前節氣**：重用首頁的節氣時程（ADR 0007：公告優先、推算補位）與「依讀者當下時間選出已交節的最近一個」邏輯。時程於建置時嵌入頁面，由瀏覽器填入各節氣今年的交節日期時刻與出處標示，並標記目前節氣。靜態 HTML 不預填日期與目前節氣（ADR 0006 的取捨延伸）；不自動捲動。首頁與總覽頁共用這段邏輯，不複製。
- **首頁節氣列**：改為連到 `/solar-terms/#<識別值>`。
- **空集合規則**：正式內容目錄沒有節氣資料時，不產生總覽頁、首頁節氣列不加連結，內容檢查通過；只要有資料就必須 24 筆齊全。讓程式可先合入，正式說明待來源核准後再上。
- **搜尋**：總覽頁納入 Pagefind 索引。
- **入口**：只有首頁節氣列。主選單不新增項目；食材條目頁不反向顯示當令節氣。
- **內容檢查**：新增節氣檢查模組，併入 `pnpm check:content`：24 個識別值齊全且無多餘；每筆通過 schema；每筆的說明在來源紀錄有對照，且對照網址列於 `sources`；當令食材只指向已發布食材條目；來源網址不得出現在建置輸出（沿用既有洩漏檢查）；頁面文案納入既有的 AI／試做文案檢查。
- **ADR 0008 補依賴檔案**：實作完成後，在 Falsified if 段落以反引號補上節氣資料、頁面與檢查模組的路徑。

## Testing Decisions

- 只測外部行為：頁面上讀者看得到的內容與互動、內容檢查回報的 issues；不測內部函式拆法或資料轉換細節。
- **接縫一：e2e（Playwright）**，以固定菜譜與固定節氣資料建置後測 `/solar-terms/`，比照 `e2e/home-season.spec.ts` 用 `page.clock` 固定時間。涵蓋：四季分組與立春起排序、24 個節氣都有插畫與替代文字、說明與當令食材連結、空食材節氣不顯示空清單、目前節氣標記與交節時刻切換、今年日期與出處標示（公告年份顯示「資料：中央氣象署」、推算年份顯示「依天文推算」）、首頁節氣列連到正確錨點、搜尋找得到節氣名、手機寬度無橫向捲動、既有 a11y 檢查。
- **接縫二：內容檢查單元測試**，給 fixtures 目錄、斷言回傳 issues，比照 `tests/content-checks-topics.test.ts`。涵蓋：缺節氣、多出未知識別值、schema 錯誤、說明無來源對照、對照網址未列於 sources、食材指向不存在或未發布條目、來源網址洩漏到輸出。
- schema 錯誤經由內容檢查接縫驗證，不另開 schema 單元測試。
- fixtures：e2e 用的節氣資料需 24 筆齊全，部分節氣帶當令食材（指向既有 fixture 食材條目）、部分為空。

## Out of Scope

- 每個節氣的個別頁面（之後內容累積再拆頁）。
- 主選單「節氣」項目；食材條目頁反向顯示當令節氣。
- 養生、健康功效說法；民俗與天文的延伸長文。
- 列出尚無食材條目的食材；由產期文字自動推導節氣對應。
- 重繪插畫或新插畫風格。
- 依節氣推薦菜譜（只連食材條目；菜譜由食材條目再連出）。
- 頁面自動捲動到目前節氣。
- 搜尋結果直接跳到節氣錨點。

## Further Notes

- **前置條件**：寫節氣說明前，先依 `topic-writing` 流程列出候選來源（優先中央氣象署的節氣說明）請站主核准；未核准前只能完成程式與 fixtures，不寫正式說明。若找不到單一合適來源，退回「第一版不寫說明」並回報站主。
- 正式說明送審前依 `de-ai-voice` 去 AI 味，只改腔調不改事實。
- 當令食材初版由站主挑選；實作者可依食材條目產期文字提出建議清單，但須經站主確認。
- 依 AGENTS.md：提交前跑 `pnpm check && pnpm test && pnpm test:e2e`，開 PR 前跑 `pnpm check:merge`；不得推送 `main` 或合入 PR。

# 專題：規格

Status: open
Label: ready-for-agent

詞彙依 `GLOSSARY.md`：**專題**、**選題參考**、**核准來源**、**菜譜**、**食材條目**。本規格由 2026-10-07 的 grill 討論整理而成。

## Problem Statement

站主想在菜譜與食材條目之外，寫一些跨越多道菜的料理知識，例如逆紋切肉的道理、熱鍋冷油適用的場合、什麼時候下鹽。這類內容放不進菜譜（只描述一道菜），也放不進食材條目（只談單一食材），目前網站沒有地方可以放。

站主看到值得整理的外部文章時（例如一篇 22 條做菜原理的 X 長文），也沒有一套流程能把它變成站上的內容。原文是他人的著作，本身又是 AI 輔助產出，有幾條是沒經過查證的民間口訣，照搬會有著作權問題，也會把錯誤一起帶過來。代理寫出來的文字還常帶 AI 腔：清單體、空泛的總結句、捏造的個人經驗，站主得逐句改。

## Solution

網站新增一種內容「專題」：一篇獨立的料理知識文章，有自己的列表頁和文章頁，導覽列可以進入，搜尋找得到。專題可以連到相關菜譜和食材條目，但不重寫完整的料理步驟。

外部文章只當選題參考，用來決定題目和架構，並在頁面底部公開標註原作者。專題裡的每項事實都要另外找核准來源查證，來源紀錄裡逐段列出各節採用的來源，讓站主可以一段一段審。

repo 內新增兩個 skill：
- `topic-writing`：規範專題從選題到送審的整個流程。
- `de-ai-voice`：專題、菜譜、食材條目三種寫作共用的去 AI 味步驟。

代理只用資料整理的口吻寫，不替站主捏造經歷；站主的個人心得由站主自己加進內文。

## User Stories

1. 身為讀者，我想從導覽列進入「專題」，以便找到料理原理類的文章。
2. 身為讀者，我想在專題列表頁看到每篇專題的標題、短介、封面圖和發布日期，以便挑想讀的那篇。
3. 身為讀者，我想看到列表依發布日期由新到舊排列，以便先看到最新的專題。
4. 身為讀者，我想在專題頁讀到完整內文，以小節標題分段，以便快速跳到想看的原理。
5. 身為讀者，我想看到每條原理說明背後的原因，而不只是口訣，以便遇到沒有菜譜的情況也能自己判斷。
6. 身為讀者，我想在專題中點進相關菜譜，以便直接看一道應用這些原理的菜。
7. 身為讀者，我想在專題中點進相關食材條目，以便查那項食材的選用與保存。
8. 身為讀者，我想在專題頁底部看到選題參考的作者與連結，以便讀原文，也知道這篇從哪裡得到啟發。
9. 身為讀者，我想用「逆紋」「爆香」這類詞搜尋時也找到專題，以便不必知道內容放在哪個區塊。
10. 身為讀者，我想在用菜譜分類篩選搜尋結果時不被專題干擾，以便照舊只找菜譜。
11. 身為讀者，我想在搜尋結果中分辨哪些是專題、哪些是菜譜，以便決定點哪一個。
12. 身為讀者，我想在手機上順暢閱讀專題，沒有橫向捲動，以便在廚房邊看邊做。
13. 身為讀者，我想讓專題頁的封面插畫和菜譜成品圖風格一致，以便整個網站看起來是同一個地方。
14. 身為使用螢幕閱讀器的讀者，我想讓專題封面圖有替代文字、內文有正確的標題層級，以便理解頁面結構。
15. 身為站主，我想用 Markdown 寫專題，以便長篇散文好寫好改。
16. 身為站主，我想讓新專題預設是草稿，正式建置看不到，以便核准前不會被讀者看到。
17. 身為站主，我想在開發伺服器看到草稿專題，以便審閱時預覽實際頁面。
18. 身為站主，我想讓已發布專題一定有封面圖，以便列表頁不會缺圖。
19. 身為站主，我想讓相關連結只能指向已發布的菜譜和食材條目，以便讀者不會點到不存在的頁面。
20. 身為站主，我想讓 schema 擋下打錯的相關連結識別值，以便在建置前就發現錯字。
21. 身為站主，我想讓已發布專題沒有核准來源時內容檢查失敗，以便沒查證的內容不會上線。
22. 身為站主，我想在來源紀錄裡看到每一節採用了哪些來源，以便逐段審閱。
23. 身為站主，我想讓核准來源不出現在公開頁面或建置輸出，以便和菜譜一樣把來源紀錄留在內部。
24. 身為站主，我想讓封面圖受同樣的規格檢查（WebP、1536×1024、不超過 300 KB、替代文字不提餐具），以便全站圖片一致。
25. 身為站主，我想讓代理先提出候選核准來源給我核准再動筆，以便控制事實依據。
26. 身為站主，我想讓代理在查不到依據時刪掉或修正那條原理並回報，以便口訣類的錯誤不會被照抄。
27. 身為站主，我想讓代理不沿用選題參考的原句，以便避免著作權問題。
28. 身為站主，我想讓代理不寫第一人稱經驗，以便站上不出現捏造的經歷。
29. 身為站主，我想自己在內文加入個人心得，以便需要時專題裡有我的聲音。
30. 身為站主，我想讓代理在送審前跑去 AI 味步驟，以便收到的稿子不必逐句改腔調。
31. 身為站主，我想讓去 AI 味的規則放在 repo 裡，以便 Codex 或其他代理也讀得到。
32. 身為站主，我想讓菜譜與食材條目寫作也接上同一個去 AI 味步驟，以便全站文字口吻一致。
33. 身為站主，我想讓去 AI 味保留事實、立場與臺灣用語，只改腔調，以便潤稿不會改壞內容。
34. 身為站主，我想讓 skill 規定每節的結構（原則、原因、怎麼做與怎麼判斷、相關菜譜），以便每篇專題讀起來一致。
35. 身為站主，我想讓 skill 給出每篇約 1,500 到 3,000 字的篇幅指引，以便專題不會長成難讀的清單。
36. 身為站主，我想把長篇選題參考依烹飪階段拆成幾篇專題，以便每篇都好查證、好審閱。
37. 身為站主，我想讓選題參考裡的完整料理示範做成正式菜譜，再由專題連過去，以便步驟只在一個地方維護。
38. 身為站主，我想讓 skill 附上送審前的自查清單，以便我知道代理已經核對過哪些事。
39. 身為站主，我想讓草稿專題留在工作分支，準備好才開 PR，以便合入 PR 就等於核准發布。
40. 身為維護者，我想讓測試用固定專題和正式內容分開，以 `TOPICS_DIR` 切換，以便 e2e 不受正式內容變動影響。
41. 身為維護者，我想讓專題的內容檢查和既有的菜譜、食材條目檢查共用同一個指令，以便部署流程不必改。

## Implementation Decisions

- **內容集合**：新增「專題」內容集合，一篇一個資料夾，資料夾名稱即識別值與網址，格式規則和菜譜相同。內文是 Markdown 加 frontmatter（不用 MDX），圖片放同一個資料夾，以相對路徑引用。內容根目錄預設為正式內容，以環境變數 `TOPICS_DIR` 切換，比照 `RECIPES_DIR` 與 `INGREDIENTS_DIR`。程式識別字一律用 `topic`。
- **專題 schema**：以工廠函式建立，比照菜譜與食材條目的 schema（接收圖片型別，方便單元測試）。欄位如下：
  - `title`、`summary`、`draft`
  - `publishedAt`（日期）
  - `hero`：`{ src, alt }`，alt 必填
  - `relatedRecipes`、`relatedIngredients`：識別值陣列，可為空
  - `references`：選題參考陣列，每筆有作者、標題、網址

  已發布專題的規定：
  - 必須有 `hero`
  - 相關連結只能指向已發布的菜譜或食材條目，草稿專題沒有這項限制
  - 第一版不做 `updatedAt` 和標籤
- **來源紀錄**：每篇專題對應一份內部來源紀錄，放在內容集合與公開輸出之外，只有內容檢查會讀，比照食材條目的來源紀錄。內容包括：
  - `sources`：核准來源清單，每筆有 `title`、`url`
  - 段落對照：小節標題對應到採用的來源網址

  選題參考不放在來源紀錄裡，它放在 frontmatter，因為要公開顯示。
- **頁面**：
  - 列表頁 `/topics/`：只列已發布專題（開發模式含草稿），依 `publishedAt` 由新到舊，每張卡片有封面、標題、短介、發布日期。
  - 文章頁 `/topics/<識別值>/`：依序是封面、標題、發布日期、內文、相關菜譜與食材條目、底部的選題參考。
  - 導覽列在「食材介紹」之後加一項「專題」。
  - 首頁不變。
- **草稿處理**：沿用菜譜既有的草稿機制。正式建置排除草稿專題，開發伺服器顯示。
- **搜尋**：專題頁的標題、短介、內文進 Pagefind 索引，圖片替代文字照舊排除。專題頁加 `type:topic` 篩選標記；既有的菜譜分類篩選語意不變，只套用在菜譜上。搜尋結果要讓讀者分辨專題和菜譜。
- **內容檢查**：既有的 `check:content` 加上專題規則：
  - 已發布專題的來源紀錄存在，且至少有一筆核准來源
  - 段落對照中的每個網址都列在 `sources` 裡
  - 封面圖規格（WebP、1536×1024、不超過 300 KB）
  - 封面替代文字不提餐具
  - 草稿專題不出現在建置輸出
  - 核准來源網址不洩漏到建置輸出

  候選池門檻（`--launch`）不受專題影響。專題來源紀錄目錄以環境變數切換，比照既有的 `SOURCES_DIR`。
- **`de-ai-voice` skill（repo 內）**：以全域 `humanize-writing` 的繁中規則為底，精簡成站點版本。只改腔調，保留事實、立場、臺灣用語。站點限制包括：
  - 不宣稱試作
  - 不寫療效
  - 不用促銷語氣
  - 不捏造第一人稱經驗
  - 不寫空泛的總結句
  - 不硬套清單體

  專題、菜譜、食材條目三種寫作共用。
- **`topic-writing` skill（repo 內）**，步驟如下：
  1. 確認選題參考與範圍。長篇參考依烹飪階段拆成多篇，完整料理示範交給 `recipe-making` 做成菜譜。
  2. 代理提出候選核准來源，站主核准。
  3. 逐條查證，填好段落對照。查不到依據的原理刪掉或修正，並回報站主。
  4. 撰寫，每節依「原則、原因（機制）、怎麼做與怎麼判斷、相關菜譜」的結構，每篇約 1,500 到 3,000 字。不沿用選題參考的原句，不寫第一人稱。
  5. 跑 `de-ai-voice`。
  6. 逐項完成自查清單。
  7. 維持草稿，送審 PR。

  skill 裡註明：個人心得只能由站主撰寫。
- **既有 skill 與專案守則**：`recipe-writing` 和 `ingredient-writing` 在送審前加一步呼叫 `de-ai-voice`，只改步驟說明，不回頭重寫已發布內容。`AGENTS.md` 同步更新目錄結構、環境變數和寫作 skill 清單。
- **交付切分**：分成三個 PR。
  - (1) 網站功能
  - (2) 兩個新 skill，以及既有 skill 的接線
  - (3) 第一批內容：依烹飪階段拆成四篇專題（備菜與預處理、熱鍋與起鍋油、火候與調味、看熟度與脫離菜譜），以及「辣椒炒肉」菜譜

  (1) 和 (2) 互不依賴、可並行；(3) 要等前兩個合入。

## Testing Decisions

- 好的測試只驗證外部行為：給定內容與建置輸出，檢查報出的問題或頁面上讀者看得到的東西。不測內部函式的拆法。
- **專題 schema 單元測試**：直接對工廠函式產生的 schema 跑 safeParse，涵蓋以下情況：
  - 完整草稿可以沒有圖片
  - 已發布專題缺 `hero` 時失敗
  - 識別值格式
  - `references` 欄位
  - 日期欄位

  前例：食材條目與菜譜的 schema 測試。
- **內容檢查測試**：以暫存的建置輸出與來源紀錄目錄跑檢查執行器，涵蓋以下情況：
  - 已發布專題缺來源紀錄或沒有核准來源
  - 段落對照引用了未列出的網址
  - 封面圖規格不符
  - 替代文字提到餐具
  - 草稿出現在輸出
  - 來源網址洩漏

  前例：食材條目、來源紀錄、圖片、洩漏的內容檢查測試。
- **相關連結驗證**：已發布專題連到草稿菜譜或食材條目時要失敗。歸在 schema 或內容檢查哪一層由實作決定，但測試要從該層的公開入口驗證。前例：已發布食材條目必須連到已發布菜譜的檢查。
- **e2e（Playwright，chromium）**：測試用固定專題至少三篇，其中一篇草稿；以 `TOPICS_DIR` 指定。涵蓋以下情況：
  - 列表頁只顯示已發布專題，並依發布日期排序
  - 專題頁顯示內文小節、相關連結、選題參考
  - 導覽列有「專題」並導向列表頁
  - 搜尋專題內文的詞能找到專題，菜譜分類篩選結果不含專題
  - 草稿頁在正式建置下不存在
  - 手機寬度沒有橫向捲動
  - 無障礙檢查通過

  前例：食材條目頁、搜尋、手機導覽與無障礙的 e2e。
- skill 屬於文件，不寫自動測試，由站主審閱 PR (2) 把關。PR (3) 的內容由 `check:content` 與站主逐段審閱把關。

## Out of Scope

- 系列：一個專題底下有多篇文章
- 標籤、分類、`updatedAt`
- 首頁露出專題
- 菜譜頁與食材頁反向顯示「相關專題」
- MDX 和內文嵌入元件（例如菜譜卡片）
- 轉載或翻譯外部文章；使用選題參考的圖片
- 回頭重寫已發布的菜譜和食材條目文字
- 專題的評論、分享、收藏功能

# 首頁隨機推薦與菜譜頁相關菜譜規格

Type: spec
Status: open
Label: ready-for-agent

本規格整理自 2026-10-10 的 grill-with-docs 討論。詞彙見 `GLOSSARY.md`〈瀏覽〉：「隨機推薦」指首頁每次開啟隨機抽出的區塊，「相關菜譜」指菜譜頁依內容相似挑出的菜；兩者不可混用。本規格不改 ADR 0005（首頁大圖每次開啟隨機），隨機推薦沿用同樣的「瀏覽器端每次開啟才抽」做法。

## Problem Statement

已發布菜譜到了 196 道（非湯料理 142、湯 37、主食 21 道，含草稿共 200）。首頁清單依標題排序，每批顯示 20 列，讀者不搜尋、不篩選時，幾乎只看得到標題排在前面的菜，後段的菜沒有曝光機會。沒有明確想煮什麼的讀者，除了一張隨機大圖之外，沒有其他「給我幾個點子」的入口。

讀者看完一道菜之後，菜譜頁只連到相關食材條目與專題，沒有通往其他菜譜的路，只能回首頁重新找。

## Solution

首頁加一個隨機推薦區塊（寬螢幕在菜譜清單之前，手機在清單第一批之後）：每次開啟頁面時從已發布菜譜中隨機抽 6 道，以卡片呈現成品圖、菜名與料理主角標籤，旁邊有「換一批」按鈕。讀者選了料理主角篩選時，只從該類抽；輸入搜尋字時區塊隱藏。菜譜清單本身維持標題排序與顯示更多，不受影響。

每道菜譜頁最底部加「也可以試試」，列出 4 道相關菜譜：優先挑料理主角相同、共用較少見主要材料的菜。這份清單在建置時算好，同一次建置內固定，不看讀者的行為或收藏。

## User Stories

1. As a 首頁讀者, I want 在清單上方看到幾道隨機挑出的菜, so that 我不搜尋也能發現清單後段的菜。
2. As a 首頁讀者, I want 每次開啟首頁都看到不同的隨機推薦, so that 回訪時有新的點子。
3. As a 首頁讀者, I want 按「換一批」換成另外 6 道, so that 這批沒有想煮的菜時可以再看一批。
4. As a 首頁讀者, I want 換一批時優先出現還沒看過的菜, so that 不會一直看到同幾道。
5. As a 首頁讀者, I want 這一輪所有候選都出現過後重新開始, so that 按鈕不會失效。
6. As a 首頁讀者, I want 隨機推薦不重複大圖那道菜, so that 首屏不會同一道菜出現兩次。
7. As a 首頁讀者, I want 卡片顯示成品圖、菜名與料理主角標籤, so that 一眼判斷是不是我想煮的菜。
8. As a 首頁讀者, I want 點卡片進到該菜譜頁, so that 可以直接開始看做法。
9. As a 首頁讀者, I want 選了「海鮮」等篩選時，隨機推薦也只從海鮮抽, so that 推薦跟我選的方向一致。
10. As a 首頁讀者, I want 切換篩選時，隨機推薦立刻從新的類別重新抽, so that 不會殘留上一類的菜。
11. As a 首頁讀者, I want 輸入搜尋字時隨機推薦隱藏, so that 搜尋結果不被推薦區塊打斷。
12. As a 首頁讀者, I want 清除搜尋字後隨機推薦再出現, so that 回到瀏覽狀態時仍有點子可看。
13. As a 首頁讀者, I want 篩選後候選不足 6 道時看到全部候選, so that 區塊不會出現空位或重複的卡片。
14. As a 首頁讀者, I want 候選不超過一批時看不到「換一批」, so that 不會按了沒反應。
15. As a 首頁讀者, I want 沒有任何候選時整個區塊消失, so that 不會看到空的標題。
16. As a 手機讀者, I want 隨機推薦是一列可以橫向滑動的卡片, so that 不會把菜譜清單推到很下面。
17. As a 桌機讀者, I want 隨機推薦一列排 6 張卡, so that 一眼看完一批。
18. As a 讀者, I want 隨機推薦的圖片延遲載入, so that 首頁大圖與首屏速度不受影響。
19. As a 鍵盤與螢幕報讀讀者, I want 隨機推薦有標題、卡片是可聚焦的連結、「換一批」是按鈕, so that 我能和其他讀者一樣使用。
20. As a 讀者, I want 換一批之後螢幕報讀知道內容已更新, so that 我不用重新瀏覽整個區塊才發現變了。
21. As a 沒有 JavaScript 的讀者, I want 隨機推薦不顯示，清單照常完整, so that 頁面不會出現壞掉的區塊。
22. As a 讀者, I want 從菜譜頁按上一頁回首頁時，清單仍回到離開前展開的數量與捲動位置, so that 隨機推薦不破壞顯示更多既有的返回行為。
23. As a 菜譜頁讀者, I want 在頁面最底部看到 4 道相關菜譜, so that 看完這道可以接著看類似的菜。
24. As a 菜譜頁讀者, I want 相關菜譜優先是料理主角相同的菜, so that 看完魚片看到的是其他魚片或海鮮。
25. As a 菜譜頁讀者, I want 相關菜譜以共用較少見主要材料的菜優先, so that 推薦是因為都用了鯛魚片，而不是因為都放了蔥薑蒜。
26. As a 菜譜頁讀者, I want 主食推薦主食、湯推薦湯, so that 推薦的上桌用途一致。
27. As a 菜譜頁讀者, I want 沒有共用材料的菜仍看得到同料理主角的 4 道菜, so that 每頁都有地方可以接著看。
28. As a 讀者, I want 各頁的補位菜不同，不是每頁都出現同一道, so that 推薦不會集中在標題排前面的少數幾道。
29. As a 讀者, I want 相關菜譜不出現本頁自己, so that 推薦都是新的菜。
30. As a 讀者, I want 相關菜譜不出現草稿, so that 不會點到不存在的頁面。
31. As a 讀者, I want 用菜名搜尋時，結果不會因為某頁底部的相關菜譜列了這道菜而多出那一頁, so that 搜尋結果只列真正相關的頁面。
32. As a 讀者, I want 相關菜譜卡片顯示成品圖與菜名, so that 跟首頁卡片看起來是同一套。
33. As a 站主, I want 相關菜譜完全由規則產生, so that 新增菜譜時不用回頭維護其他菜的推薦。
34. As a 站主, I want 香辛料與水的排除清單集中在一處, so that 發現某種材料墊高分數時，送一個小 PR 就能修。
35. As a 站主, I want 同一次建置的相關菜譜固定不變, so that 審閱 PR 時看到的推薦就是上線後的推薦。
36. As a 站主, I want 隨機推薦不收集讀者資料, so that 網站維持不追蹤個人行為。
37. As a 站主, I want 隨機推薦和相關菜譜分兩個 PR 送審, so that 可以分別看、分別合入。

## Implementation Decisions

**交付順序**：拆兩張票、兩個 PR。先做相關菜譜（純建置時計算，風險低），再做隨機推薦。兩者不共用演算法模組；卡片外觀可以共用一個卡片元件。

**相關菜譜模組**（新的純函式模組）：

- 介面：輸入全部已發布菜譜（識別值、類別、料理主角、材料），輸出「識別值 → 依序 4 個相關菜譜識別值」。草稿在呼叫前就排除，與現有取得已發布菜譜的路徑相同。
- 分組：非湯料理以料理主角（`dishKinds`）判斷是否同組，只要有任一主角相同就算同組；主食與湯以類別判斷。排序先排同組，再排不同組。
- 主要材料：一道菜的材料扣掉「調味」「醃料」兩組（組名去掉頭尾空白後比對），再扣掉排除清單中的名稱。名稱只去掉頭尾空白後完全比對，不做同義詞。
- 排除清單：放在模組內的常數，初版是水、外鍋水、高湯、蔥、青蔥、蔥花、蔥段、薑、薑片、薑絲、老薑、蒜、蒜頭、大蒜、蒜仁、蒜末、蒜泥、辣椒、紅辣椒、乾辣椒、辣椒末、九層塔、香菜。要修改就送 PR。
- 分數：把兩道菜共用的主要材料逐一加上 `ln(已發布菜譜數 ÷ 用到該材料的菜數)`，越少菜用到的材料權重越高。
- 排序規則（來自原型）：同組在前 → 分數高在前 → 同分時依雜湊排序。雜湊用「本篇識別值＋候選識別值」計算，要穩定（同一份輸入一定得到同一個順序），不能用標題排序，否則補位會集中到同幾道菜。只取同組或分數大於 0 的候選，取前 4 道；全部候選少於 4 道時有幾道列幾道。
- 原型結果（2026-10-10，196 道真實資料）：宮保蝦仁 → 豆腐蝦仁、蝦仁炒蛋、XO 醬炒雙鮮（共用蝦仁）；橙汁魚片 → 杏仁煎魚片、蒜味炸魚片（共用鯛魚片）；酒蒸肉丸 → 瓜仔肉、洋蔥炒豬絞肉、蒼蠅頭（共用豬絞肉）。排除清單上線前，宮保蝦仁排第一的是宮保雞丁，靠的全是蔥薑蒜辣椒。共有 42 道菜前 4 名的分數全是 0，靠同組補位。
- 菜譜頁：在相關食材與專題之後加「也可以試試」區塊，整個區塊標上 `data-pagefind-ignore`。

**為什麼不結構化標記主要材料**：準確度的瓶頸是材料名稱是自由文字（牛肉／牛腱、蒜頭／大蒜／蒜仁），根本的解法是在菜譜 schema 加「主要材料」欄位，但那會動到內容的公共介面，196 篇都要逐一補標。這次的判斷是：規則加上同組補位已經夠用，代價不值得。日後要加這個欄位，屬於重新決定，要另外 grill。食材條目的 `relatedRecipes` 只連到 36 道菜，覆蓋率太低，不作為推薦依據。

**隨機推薦模組**（新的純函式模組，瀏覽器端腳本呼叫）：

- 介面：輸入候選識別值清單、這一輪已出現過的識別值、亂數來源，輸出下一批（最多 6 個）與更新後的已出現集合。不讀 DOM，也不呼叫全域 `Math.random`，亂數由呼叫端傳入。
- 抽批規則：先從還沒出現過的候選抽；不足一批時，把已出現集合清空、開始新的一輪，用新一輪的候選補滿，且同一批內不重複。候選數 ≤ 6 時直接回傳全部。
- 候選範圍：已發布且有成品圖的菜譜，排除大圖那道；有料理主角篩選時，只取帶有該分類的菜（分類判斷與大圖、清單篩選共用現有的分類函式）。
- 首頁接線：候選資料在建置時寫進頁面（站主決定：候選資料由建置時輸出的靜態 JSON 檔提供，首頁載入後才抓取、由腳本組卡片；未選中的圖片不下載。理由：196 份 `<template>` 讓首頁 gzip 從 76.5 KB 增至 103.6 KB，改內嵌 JSON 仍有 99.5 KB（srcset 網址含雜湊、壓縮有限）；延後載入讓首頁回到原大小，資料不擋首屏，也不給無 JavaScript 的讀者）。開啟時抽第一批；篩選改變時重抽並重置這一輪；有搜尋字時隱藏區塊；候選數 ≤ 6 時隱藏「換一批」，0 道時隱藏整個區塊。沒有 JavaScript 時不顯示區塊。
- 位置與版面：寬螢幕放在菜譜清單之前，一列 6 張；手機（< 40rem）放在清單第一批之後、「顯示更多」附近，一列橫向捲動。2026-10-10 站主決定：放在清單前會把手機第一列推下 167px，違反〈手機首屏露出第一列菜譜〉規格（第一列底端 ≤ 844px），該首屏測試不改。手機版，高度約一張卡片。圖片延遲載入，不能搶走大圖的 `fetchpriority`。
- 無障礙：區塊有標題（暫定「今天煮什麼」），「換一批」是 `<button>`；換批後用 live region 或移動焦點的方式讓報讀知道內容已更新。
- 不寫入 history state、localStorage 或 sessionStorage，不影響顯示更多既有的返回位置還原機制。

**沒有 ADR**：這次的決策都容易改回，不符合 ADR 門檻。不結構化標記主要材料的取捨記在本規格。

## Testing Decisions

- 好的測試只驗證外部行為：純函式的輸入與輸出、建置後頁面讀者看得到的內容；不斷言內部資料結構或演算法的中間值。
- 相關菜譜模組的單元測試（Node 內建測試執行器）：同組優先於跨組；稀有材料勝過常見材料；調味、醃料組與排除清單中的材料不計分；完全比對、不做同義詞；不含本篇自己；同分時的雜湊順序穩定，而且不是依標題排序（設計一組資料，讓依標題排序與依雜湊排序的結果不同）；候選不足 4 道的情況；輸出與輸入順序無關。
- 真實資料回歸：讀正式內容，斷言宮保蝦仁、橙汁魚片、酒蒸肉丸的前幾名包含原型找到的菜，並斷言沒有任何一道菜的相關菜譜包含草稿或自己。先例：`tests/recipe-classification.test.ts` 讀正式內容做回歸。
- 隨機推薦模組的單元測試：傳入固定的亂數序列；候選不足 6 道時回傳全部；一輪之內不重複；一輪結束後重新開始；同一批內不重複；輸入不被改動。先例：`tests/home.test.ts` 的顯示更多純函式（`showMore`、`truncateRows`）。
- e2e（Playwright，預設站台）：首頁覆寫 `Math.random`（先例：`e2e/homepage.spec.ts` 的大圖測試），斷言隨機推薦張數、不含大圖那道、篩選後只剩該類、有搜尋字時隱藏、清除後再出現；固定菜譜扣掉大圖只剩 5 道候選，剛好可以驗證「不足一批時全部顯示、沒有換一批按鈕」。「換一批」的不重複行為交給單元測試，或在顯示更多站台（每批 1 道）的設定下另外測，由實作時判斷是否值得。菜譜頁斷言相關菜譜區塊存在、不含本頁與草稿、連結可以點；搜尋測試補一筆，確認相關菜譜的標題不會讓別頁命中（先例：`e2e/search.spec.ts`）。
- 版面：隨機推薦上線前跑 `pnpm measure:mobile`，回報首頁第一列清單被推下多少，由站主決定是否接受；`e2e/mobile-list.spec.ts` 與 `e2e/a11y.spec.ts` 要維持全綠。
- 固定菜譜不新增。

## Out of Scope

- 依收藏、瀏覽紀錄或任何讀者行為推薦；不收集讀者資料。
- 時令推薦（當令食材、節氣）：節氣資料目前是空的，等資料齊了再另外規劃。
- 依手邊食材查詢（「冰箱有什麼」）：現有的搜尋加篩選先撐著。
- 菜譜 schema 新增主要材料或手動指定相關菜譜的欄位，以及材料同義詞表。
- 把首頁菜譜清單改成隨機排序。
- 首頁大圖的「換一道」按鈕，以及改動 ADR 0005 的大圖行為。
- 配菜頁與專題頁的推薦。

## Further Notes

- 原型腳本（材料 IDF＋排除清單＋同組優先）是一次性的，沒有放進 repo。實作時以本規格的規則為準，再用真實資料回歸測試確認結果跟原型一致。
- 料理主角標籤與分類判斷依 `GLOSSARY.md`、ADR 0010 和 `docs/recipe-classification.md`。`vegetable`／`protein` 是配餐角色，不參與相關菜譜的分組。
